# nil-vcpkg-ports Agent Guide

Use this guide when adding a new `nil-*` vcpkg port, importing an upstream GitHub tag, wiring dependencies, or updating registry version metadata.

## Scope

- Work only on the requested port and the metadata files required to register it.
- Preserve unrelated user changes in the worktree.
- Do not commit, reset, checkout, or delete existing user changes.
- Do not invent an upstream version, tag, dependency, or source hash.

## Repository Conventions

- Port directories are `ports/<port-name>/` and normally contain `vcpkg.json`, `portfile.cmake`, and `port.cmake`.
- Nil ports use GitHub repositories under `https://github.com/njaldea/<port-name>`.
- Standard manifest dependencies are host dependencies on `vcpkg-cmake` and `vcpkg-cmake-config`, followed by the requested project dependencies.
- Standard portfiles use `vcpkg_from_github` with `REF "v${VERSION}"`, a verified SHA-512 archive hash, and `HEAD_REF master`.
- Standard CMake fragments call `vcpkg_cmake_configure`, `vcpkg_cmake_install`, `vcpkg_cmake_config_fixup`, and `vcpkg_install_copyright`, then remove debug and top-level library artifacts when appropriate.
- Registry metadata lives in `versions/n-/<port-name>.json`, `versions/baseline.json`, and generated `VERSIONS.md`.

## Port Addition Workflow

1. Inspect the closest existing port before editing. Prefer a port with similar upstream build/install behavior and dependencies.
2. Inspect the upstream repository and identify the exact release tag, version, project name, install destinations, license path, and required runtime/build dependencies. Use the requested port name for vcpkg metadata, even if the upstream CMake project has a different name.
3. Download the exact GitHub archive referenced by the portfile and calculate its SHA-512 with `curl -LsS <archive-url> | sha512sum`. Never reuse a hash from another version or port.
4. Create or update the port files with the smallest change matching local conventions. Add only dependencies required by the upstream project or explicitly requested by the user.
5. Validate the manifest and metadata with `jq`, run `./scripts/versions` to regenerate `VERSIONS.md`, and run `git diff --check`.
6. Register the port in `versions/baseline.json` with `port-version: 0` and create its version file. For an uncommitted new port, derive its git tree from the port files using Git object hashing and record that tree in `versions/n-/<port-name>.json`; do not use the archive hash as the git tree.
7. Check editor diagnostics for edited JSON and CMake files. If a vcpkg executable is available, run the narrowest package install or manifest validation for the new port. Otherwise state that the package-level check was unavailable.
8. Report changed files, upstream tag/version, dependency choices, validation results, and any pre-existing unrelated worktree changes. Do not commit.

## Metadata Rules

- Keep `versions/baseline.json` and `VERSIONS.md` synchronized with the manifest version.
- `VERSIONS.md` is generated by `./scripts/versions`; do not hand-format it unless the script is unavailable.
- The `git-tree` value is the tree object for the port directory contents, not the SHA-512 archive hash.
- If the port directory contains files beyond the standard three, include them in the tree calculation.
- If a port version or tag was relocated, re-download that exact tag archive and replace only the SHA-512 unless broader metadata changes are requested.

## Completion Report

Summarize the implementation concisely. Include the port name, version/tag, dependencies, files changed, validation commands run, and any checks that could not be run.
